## 3. Verification methodology

Run environment: Google Colab, Python 3.13.18, pandas 2.2.3, numpy 2.4.6. Verifier `h1_ait_verify.py` (MD5 `d5eb4d04cd7beaf6728d5fe1573a72d5`), chunk size 200,000 rows.

1. **Archives**: the verifier computed the MD5 and byte size of every downloaded file and compared them with the values Zenodo lists. It ran `zipfile.testzip()`, which reads every member and checks its CRC-32. All files are checked, and a failure is recorded rather than stopping the run.
2. **CSVs**: each CSV was streamed straight out of its ZIP with `pandas.read_csv(chunksize=200000, dtype=str, na_filter=False, on_bad_lines='error')`. The archives were never modified and only one chunk was in memory at a time. Newlines were counted in the same pass, so the pandas row count can be reconciled against the physical line count.
3. **Labels**: `label_info.txt` was parsed into its four sections (Benign/Malicious × TCP/UDP). The mapping is **exact** (case- and whitespace-sensitive) and **protocol-aware**: TCP files use the TCP sections and UDP files use the UDP sections. Any other value is *unmapped* and is never counted as benign.
4. **Quality**: per file, the verifier counted empty cells and NA-like tokens (`NA`, `N/A`, `nan`, `NaN`, `null`, `NULL`, `None`, `-`), exact duplicate rows, and groups of rows with identical features but different binary labels (both via 64-bit row hashes over the full file). It also cross-checked the protocol in each filename against the schema and recorded the timestamp range.
5. **Report**: this file is generated from the CSV/JSON outputs by `h1_make_report.py`. The unmapped-row profile in section 7 is recomputed from the original ZIP.

**Assumptions**

- The publisher's labels are taken as ground truth. H-1 checked that they are consistent and complete, not that each label is correct.
- The protocol comes from the file name (`tcp_*` / `udp_*`) and was cross-checked against the schema (TCP files contain `c_syn_cnt`, `c_fin_cnt` and `c_rst_cnt`; UDP files do not).
- Duplicate and conflict detection relies on 64-bit hashes of full rows. The collision probability at this scale is negligible but not zero.

**Recommendations for later tasks** (not done in H-1)

- H-3: exclude the 942 unmapped flows (or ask the publisher) and state this in the labelling rule. Never map them to 0.
- H-3/H-4: decide explicitly whether `tcp_nocomplete` flows are used. They are 99.0% suspicious, so a model that can tell which file a flow came from (or can see the features that define ‘non-complete’) gets a near-trivial shortcut. Report results with and without them.
- H-4: the 3 schemas need either a common feature subset or per-protocol handling. Treat `-`/`---` placeholders as categorical ‘not applicable’ values. Drop IPs and timestamps, as the tracker already requires.
- M-3/H-6: the classes are imbalanced and vary by network (5.2%–45.3%). Use class weights and report per-network metrics.

## 9. Limitations

- MD5 proves the files are identical to what Zenodo publishes. It does not protect against a malicious publisher, and MD5 is not collision-resistant. SHA-256 was not available from the record.
- The numeric type profile (`mixed_or_text_columns_first_chunk_json`) covers only the first 200,000 rows of each file. Empty-cell, NA-token, duplicate and label counts cover every row.
- Only exact duplicates *within* a file were counted; cross-file and cross-network duplicates were not.
- H-1 did not check whether labels are correct in time against the attack schedule; that belongs to label auditing (H-3) and Reem's R-6.
